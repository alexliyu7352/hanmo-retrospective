# 三国立志型沙盒游戏设计方案 v0.1

**文档日期：2026年9月9日**  
**文档性质：总体游戏设计（GDD）／供评审的推荐基线**  
**项目工作名：汉末行记。仅用于区分文件，不代表已经确定正式名称。**

> 玩一个人的三国人生，而不是从第一天起管理一个国家。
>
> 核心循环：旅行与见闻 → 城市生活与交往 → 承担任务／经营／修业 → 获得本领、人脉与资格 → 改变身份和行动权限 → 进入新的生活与冲突。

## 0. 文档边界与决策状态

### 0.1 用户已经提出的目标

以《太阁立志传5》为玩法参照，主题改为三国；尽量保留其核心游玩方式；支持跨平台，并提供网页版本。用户已要求继续制定设计方案。

### 0.2 本文提出、尚未逐项确认的推荐基线

单机优先；2D大地图与城市场景；人物立绘对话；保留修业小游戏、卡片收集、个人战与合战；使用Godot 4.x与GDScript；网页与Linux从首个可玩版本同步验证；初期不依赖账号与游戏服务器。

“同意继续设计”不等于用户已经确认本文每一条数值、人物规模、工作名或版本范围。这些内容是相互一致、可以评审的推荐方案。文中的规模、概率边界、性能预算和战斗尺寸均为设计目标，不是现有成果、性能实测或平衡结论。

### 0.3 本文提供什么

本文定义完整产品的玩法结构、第一阶段可交付范围、系统之间的作用关系、重要边界条件，以及实现时必须证明的验收标准。它不冒充逐函数程序详细设计，也不宣称已经完成全部人物考据、事件正文、数值平衡或美术资源。

当前交付是设计文档，不是可玩游戏；没有在本轮建立游戏工程、生成游戏构建或向远端仓库提交内容。

### 0.4 参考方式

以官方《太阁立志传Ⅴ DX》手册核对玩法结构，作为对《太阁立志传5》的公开官方参考，不把DX新增内容自动视为必须复制的目标。[S1—S6]

具体程序、地图表达、UI、美术、音乐、对话、任务文本和内容数据重新制作。本方案不是提取原作素材、复用原作数据或逐屏照描的改版项目。下文未特别标为“原作参考”的规则，均为本项目建议设计。

## 1. 产品定位与不能改变的核心

### 1.1 产品定位

三国题材的人物扮演与世界模拟游戏。玩家从某个身份和处境出发，在开放但有代价的选择中形成自己的人生。统一天下是可能的结局之一，不是所有职业必须汇合的终点。

### 1.2 五条设计支柱

| 支柱 | 具体要求 | 反例 |
|---|---|---|
| 人物优先 | 权限、信息和活动来自玩家本人身份 | 小吏开局就能调动整个势力 |
| 多种人生 | 仕途与非仕途都有成长、冲突和结局 | 商人最终只能靠转职君主通关 |
| 系统相连 | 时间、市场、关系、任务和战争互相影响 | 点击采购直接固定兑换功勋 |
| 世界会变化 | NPC、势力和市场有自己的状态与行动 | 所有人永远站在固定房间等玩家 |
| 收集来自经历 | 卡片记录学习、挑战、见闻与资格 | 抽卡付费获取武将或装备 |

### 1.3 明确不采用的产品方向

不做抽卡手游、放置挂机、实时动作无双、纯国战SLG、只有文本选择的互动小说，也不把它做成企业后台式的数据面板。

首个产品不包含多人联机、排行榜、赛季、体力付费、广告解锁、交易市场、账号强制登录或运行时大模型对话。它们不是本项目成立的前提。

## 2. 与参照玩法的对应关系

官方手册将人物职业、城市设施、技能与卡片、个人战、野战、攻城战和不同职业生活分别组织为主要玩法模块。[S1] 本项目应保留这种结构，而不是只保留“历史人物＋数值成长”。

| 需要保留的体验 | 本项目实现方向 | 可以调整的部分 |
|---|---|---|
| 从不同人物开始不同人生 | 历史人物、自建人物、人物解锁 | 首版可玩名单和成长节奏 |
| 大地图旅行与进入据点 | 城市、乡里、渡口、营寨和道路 | 地图美术与地理压缩比例 |
| 走访设施和人物 | 会面、交易、学习、休息、打听消息 | 设施名称和交互布局 |
| 评定／主命／立功晋升 | 定期议事、任务、考评和授权 | 采用三国语境的职位和职责 |
| 任职以外有自由时间 | 按期限安排旅行、交游和修业 | 时间粒度与提示方式 |
| 技能等级与特殊本领 | 修业、实践、师承、技艺和秘技 | 个别技能的三国化替换 |
| 收集卡片与重开动力 | 人物、技艺、秘技、战法、称号、见闻 | 美术、获得条件和解锁顺序 |
| 小游戏辅助任务和修业 | 谈价、操练、礼议等短局挑战 | 提供不伤害养成的便捷结算 |
| 个人战 | 走位、朝向、攻击范围、气势和秘技 | 原创战场、招式及数值 |
| 野战与攻城 | 部队、将领、地形、士气、战法、粮道 | 兵种与攻城设施三国化 |
| 官职决定指挥范围 | 自己一部 → 一军 → 城郡 → 势力 | 功能层级与史实官号分开 |
| 多职业转变 | 转换身份但保留人物经历 | 离职、失信和资产处理规则 |

**验收原则：** 首个区域版本可以少一些城市、人物和职业，但正式完整目标不能取消上述主要玩法，再以“同类游戏”替代“相同玩法结构”。

## 3. 版本范围：完整目标与首个可玩版本分开

本文使用P1、P2、P3表示产品里程碑，避免与设计文档版本v0.1混淆。

### 3.1 完整产品目标

一个可以持续游玩的三国世界，具备人物开局、四类组织人生与四类求道人生、个人战、野战、攻城、仕途高位治理、人物关系、动态事件和多结局。

先把一个剧本做完整，再增加其他开局年份。扩大地图和人物规模以可玩内容密度为依据，不把“几百张头像”“几十个空城市”视为完成度。

### 3.2 P1：区域可玩版

P1是可以从开局玩到阶段结局的游戏，不是只展示UI的原型；但它也不是最终完整产品。

| 项目 | 建议范围 |
|---|---|
| 剧本 | 一个汉末群雄初起的区域剧本；正式初始快照以190年为设计锚点 |
| 据点 | 12个：8座城市、2处乡里、1处渡口、1处营寨 |
| 地图结构 | 至少两条可替代旅行路线，不能是单条串联路线 |
| 人物 | 80名具名人物，20名重点内容人物；历史／原创身份清楚标识 |
| 可选开局 | 6个预置开局＋自建人物；另12个可解锁人物 |
| 组织 | 3个区域政治势力、2个商旅组织，具体历史映射在剧本资料表审校 |
| 完整道路 | 在野谋生、基层仕途至独立领队、商旅经营至首间商铺 |
| 关系 | 访问、赠礼、请求、师承、举荐、立场冲突 |
| 技艺 | 10项可成长技能；其他技能不以无效按钮占位 |
| 内容 | 10类任务模板、24个具体任务配置、18个原创事件单元 |
| 卡片 | 48张有明确获得方式和效果的卡片 |
| 小游戏 | 议价筹算、军阵操练、礼议应答，共3类 |
| 个人战 | 刀剑、长兵、弓三类武器；单挑与护送战 |
| 部队战 | 小规模野战，步兵、弓弩兵、骑兵；攻城不计入P1已交付 |
| 结局 | 仕途阶段结局、商旅阶段结局、区域见闻成就结算 |
| 存档 | 自动、手动、导入导出，网页与桌面互通验证 |
| 必须实测 | Linux和桌面网页；同时进行触摸交互验证 |

六种开局定位为两个在野处境、两个基层文武处境、两个商旅处境。它们必须改变初始任务、关系、资金与权限，不能只是换名字和属性。

P1没有完整的君主统一、全国地图、八职业全部结局、海上战争和完整攻城。游戏展示时必须如实说明区域版范围。

### 3.3 P2：扩大人生与战争范围

补全城郡治理、君主路线、攻城、另外两类组织人生，扩展有效地域与人物，完成更多桌面和Android原生验证。P2扩大的是同一个存档世界与规则体系，不另写一款只共享美术的游戏。

### 3.4 P3：完整内容与发布验证

补齐四类求道的独立后期内容和结局；完成完整剧本、跨职业事件、平台适配与发布检查。iOS交付以macOS／Xcode构建和实际设备验证为前提。[S9]

这些是依赖顺序，不是工期承诺。剧本、美术、UI和工具可在共同规范明确后并行，不必等所有程序写完才开始制作内容。

## 4. 时间、生活节奏与基本流程

### 4.1 基本时间规则

世界不会因为玩家长时间停留在菜单里而自动发展。行动消耗游戏时间，阅读信息、浏览地图和整理筛选条件不消耗时间。

初始采用“半日”为世界最小结算单位；每月30日、每年12月。这是明确的游戏化历法，不声称精确模拟汉代历法。史实事件采用时间窗口与状态条件，而不是依赖未经核验的日历日期。

| 行动 | 初始时间口径 |
|---|---|
| 查看人物、任务、路线、卡片 | 不推进时间 |
| 一次实质会面／一批交易／短期工作 | 通常半日 |
| 休息、训练、修业 | 半日至数日，确认前显示 |
| 城际旅行 | 按路线分段推进；耗时随运输方式与状况变化 |
| 个人战 | 作为所属行动的一部分，不再重复扣两次时间 |
| 部队战 | 一个完整战术轮次推进半日，结算其他世界活动 |

同一人物的同一种无实质变化访问不能通过反复开关面板无限刷关系。批量交易和同次会面的相关话题合并结算，减少无意义点击。

### 4.2 三种游玩循环

**短循环：** 发现需求 → 做一次有代价的决定 → 获得可理解的结果。例：询问粮价、选择商人、谈价并采购。

**中循环：** 安排若干日的路线和目标，兼顾任务期限、人际拜访和修业。例：去外城采购，顺路拜师，再赶回参加议事。

**长循环：** 身份变化、事业扩张、掌握新本领、形成关系网，达成个人志向或转换道路。

### 4.3 决策中断与恢复

长行动逐半日推进，遇到袭击、重大道路变化、到达目的地或需要玩家决策的事件时暂停。已经消耗的时间、物资和费用保留；未执行的行程不扣费。退出游戏不等于瞬间完成剩余旅行。

已投入但允许取消的任务，在开始前说明退出损失；不可取消的阶段必须明确提示，而不是执行后突然锁定玩家。

## 5. 世界、地图与剧本

### 5.1 地图层级

大地图负责交通、距离、势力和遭遇；城市图负责设施与人物生活；个人战与合战进入各自场景。初期不做每个城市都可自由行走的3D街区，也不模拟每一个路人。

地图是带有道路关系的2D地理空间。玩家在地图上直接选择目的地与路线，不需要把交通网络以工程图样式暴露出来。

### 5.2 首个区域

建议围绕中原与淮泗方向选择连通区域。城市名称、行政层级、所属势力、人物所在与道路位置进入专门的剧本资料表；不能把今天的城市行政范围直接套回汉末，也不能拿不同时期的人物部署拼成同一天。

P1是完整世界的局部内容切片。区域外存在边界说明与必要背景消息，但没有制作和验证的全国战争不伪装为实时模拟。区域统一只能称区域结果，不称统一天下。

### 5.3 旅行选择

每条道路具有基本耗时、通过条件、风险与运输限制。玩家可选择较短但危险的路，或更远但相对安全的路。骑乘、车辆、随从、路上天气和战争可以影响计划。

地图显示“当前所知”的路况和消息时间。没有刚获得情报，就不自动显示敌军精确兵力或人物实时坐标。重要阻断必须提供改道、等待、交涉或返回中的合理选项，不能无提示地吞掉整个委托。

### 5.4 人物所在地

人物可在城内、任职、旅行、出征、被俘、疗养或死亡。拜访时应根据状态显示实际反馈；离城人物可留下“上次听闻位置与时间”，而不是简单显示没有意义的空宅。

## 6. 人物属性、能力与身份

### 6.1 人物不是一个职业标签

人物由基础属性、技艺、身份、所属组织、经历、人际关系、资产和当前状态组成。任职身份影响责任与权限；不会禁止学习其他领域的本领。

辞官经商保留技能、人脉和个人财物；失去的是公职权限、组织资源和职位收益。背叛、毁约和侵占组织物资可能带来相应后果，不作为无成本重置。

### 6.2 五项基础属性

统率、武力、智谋、政务、魅力，基础范围1—100。高属性提供优势，但不能单独替代技能、装备、关系和行动条件。永久成长须有节制，不能短期训练把所有角色练成相同全能人物。

### 6.3 十六项完整目标技艺

| 分组 | 技艺 |
|---|---|
| 兵种与作战 | 步战、骑战、弓弩、水战 |
| 战术与实务 | 武艺、兵法、谍报、筑城 |
| 治理与交涉 | 农政、辩说、交涉、礼学 |
| 生计与专长 | 商术、运输、医术、锻造 |

技能采用0—4级，级内有经验进度。等级解锁任务、师承和卡片资格，但特殊本领还需对应经历，不能全部靠刷通用经验取得。

P1启用步战、骑战、弓弩、武艺、兵法、辩说、交涉、礼学、商术、运输。其他技艺在内容接入之前不作为玩家能投资却没有作用的系统。

### 6.4 当前状态

体力用于个人行动与个人战；疲劳影响连续工作效率；受伤、疾病、俘虏与通缉是有原因的状态。它们属于游戏内状态，不是现实时间恢复的手游体力。

个人钱财、任务资金和组织资金分开记录，但具体任务允许不同结算方式，见第10章。个人声望与恶名分开，不以一个“善恶值”简单决定全世界态度。

### 6.5 自建人物

选择姓名、头像、出身、出生年份、起始地区、属性倾向和初始专长。点数预算防止默认角色无代价全能。便利／自由创建可以作为单机选项，但与标准开局清楚区分，不需要联网防作弊。

历史人物的初始关系、年龄、任职和经历来自剧本快照；不因为玩家选择某人，就把他的所有社会关系清空。

## 7. 八条人生道路：完整目标

参考原作“加入组织的人生”和“追求技艺的人生”的区别，而不是制作八套互不相通的角色职业树。[S2]

### 7.1 四类组织人生

| 道路 | 进入与成长 | 主要决策 | 后期目标 |
|---|---|---|---|
| 仕途 | 举荐／招募 → 任职 → 领队 → 管理城郡 → 统辖或自立 | 主命、战功、内政、外交、派系与授权 | 名臣、名将、地方治理者、君主等不同结局 |
| 商旅 | 短途行商／加入商旅组织 → 独立经营 → 商铺 → 跨区域网络 | 价差、运输、信用、合作、战争中的取舍 | 富商、交通与供应网络经营者 |
| 豪侠集团 | 承接护送、救援和情报事务 → 获得信任 → 组织行动 | 情义、雇主利益、风险、暴露与立场 | 区域豪侠、独立行动组织首领 |
| 水上势力 | 参与水路运输与护航 → 掌握船队 → 控制据点与航线 | 水路、船只、商旅合作、地方势力、护航与作战 | 舟师首领、航路经营者或加入正规水军 |

豪侠、水上集团的具体组织名称属于游戏创作，不默认照搬后世门派、帮会或日本忍者机构。军事与商业利益可以交叉，但职责、资产和行动权限必须清楚。

### 7.2 四类求道人生

| 道路 | 核心循环 | 不可被删成辅助技能的后期内容 |
|---|---|---|
| 武学 | 拜师、切磋、挑战、领悟、传授 | 形成武学传承、授徒、挑战不同流派与理念 |
| 名士与学问 | 访学、礼议、讲学、收集文献、交游 | 门生、人望、地方教化、思想与立场抉择 |
| 医者 | 学习、采药与购药、诊治、医案、疑难事件 | 医馆、传授、战乱救治、独立职业结局 |
| 匠师 | 学习、采购材料、制造、委托、改良 | 名作、作坊、军民订单和技艺传承 |

医疗和制造是明确的游戏抽象，不输出真实诊疗、药方、武器制造或复杂化学操作。它们的玩法重点是判断、资源、经验、声誉和委托。

### 7.3 兼修与冲突

可以做会治病的武将、精通兵法的商人，或者辞官开馆的学者。活动能否进行由所在位置、时间、资源、资格和职责决定，不因职业标签直接灰掉所有其他生活。

同一时刻只能有一个主要组织任职契约；求道专长不占这个名额。加入敌对组织需要处理已有职责；同日不能既亲自带军远征，又亲自坐在远处商铺交易。

### 7.4 职业结局

达到职业里程碑后，可观看阶段结局并继续当前人生；主动退休、死亡或明确终局才结束整局。没有必要强迫每个人都占领所有城池。P1只完成第3章承诺的阶段结局，不声称八条道路已经全部可玩。

### 7.5 求道路线的独立事业

武学后期不是获得一张最强攻击卡就结束，而是形成自己的擅长方向，回应挑战、授徒并处理传承关系。学生成长依赖时间和传授，不能在点击收徒时直接复制师父全部技能。

名士路线通过访学、讲学、文献和处理地方争议积累影响。人物可以因学问而被征辟，也可以拒绝出仕继续传授；评价来自成果和社会反应，不要求玩家背诵真实历史知识才能过关。

医者路线区分日常诊治、疑难医案和公共救助。玩家判断游戏化症候、准备合适的游戏道具，并承担费用、疗程与病人处境的取舍。后期要经营医馆与传授，而不仅是不断使用恢复体力的药品。

匠师路线在材料、工艺、订单期限与质量之间选择。失误可能损耗材料或降低品级，经验和工坊条件改善稳定性。名作需要相应经历和条件，不能只靠无限重复点击随机出最高等级装备。

这些事业仍使用同一人物、时间、市场、关系和事件系统。P1允许使用治疗、购买等基础服务，不等于已经制作这些职业的完整经营内容。

### 7.6 豪侠与水上人生的差异

豪侠任务强调消息、目标所在、雇主可信度和完成方式：护送可以避战，救援可以交涉，探听消息可能失败或暴露。成长依靠完成承诺与建立可信关系，后期组织成员各有行动与立场，不是购买一批没有性格的数值单位。

水上人生强调船只容量、可通行水路、停靠据点、运力分配和势力关系。商运、护航和水战共用船队资源；同一艘船不能同时执行两个地点的任务。它不是把陆地地图改成蓝色，而是提供交通选择和资源约束的变化。

两者的复杂经营与独立结局属于后续范围，不为了首版职业齐全而只做一排没有系统支撑的入口。

## 8. 城市生活与设施

城市采用可点击的2D场景，建筑和人物活动构成入口。设施列表是辅助导航，不取代整个生活场景。

| 设施 | 核心活动 | 与其他系统的连接 |
|---|---|---|
| 官署 | 求职、议事、主命、交付与治理 | 任职、时间、功绩与权限 |
| 市场／商铺 | 商品、价格消息、订单和合作 | 库存、运输、战争与信用 |
| 客舍 | 住宿、恢复、临时住处、旅行消息 | 体力、疲劳、人物所在 |
| 酒肆 | 工作、传闻、结识人物和护送 | 任务、人脉、风险 |
| 人物宅邸 | 拜访、请求、馈赠、举荐和师承 | 关系、身份与技艺 |
| 学舍／讲学处 | 学习、礼议、文献与名士活动 | 技能、师承、学问路线 |
| 演武场／军营 | 切磋、操练和征募 | 个人战、部队与任务 |
| 医馆 | 治疗、药物与医疗委托 | 伤病、消费与医者路线 |
| 工坊 | 修整、购买与制造委托 | 装备、订单与匠师路线 |
| 渡口／马市 | 旅行和运输安排 | 线路、载重与费用 |

P1中医馆和工坊可以作为治疗、购买服务存在，但不能以此宣称医者和匠师职业已经完成。不同城市的设施组合、货物和人物应有差别，避免12个据点只是换背景。

新手没有钱、没有官职或任务失败时，应能通过低门槛短工重新获得基本路费和恢复机会，不因一次失误进入无解状态。

## 9. 仕途、议事、主命与晋升

### 9.1 进入组织

可通过公开招募、人物举荐、完成地方事务或被邀请进入势力。不同方式影响初始信任和关系。没有举荐不等于所有仕途永远关闭；高位人物也不会因收到一件礼物就把军队交给陌生人。

### 9.2 职位首先是权限

| 功能层级 | 可决定的事情 | 尚不能决定的事情 |
|---|---|---|
| 基层任职 | 个人行动、主命执行方式、局部提议 | 随意调动公库或其他将领 |
| 独立领队 | 分配本部战术、管理授权物资 | 越权控制全军与其他城池 |
| 城郡负责人 | 地方预算、人才安排、守备、上级授予的行动 | 无条件改变整个势力外交 |
| 区域统辖者 | 多个据点与军团、区域战略 | 未授权的全势力事务 |
| 君主 | 势力战略、任免、外交与战争 | 跳过资源、位置和部下意愿限制 |

这些是程序中的职权层级，不声称是适用于所有时期的汉末官制表。界面官号由剧本和势力定义，同一功能层级可以显示不同称谓。

### 9.3 议事节奏

初始规则为每月一次常规议事，另有战争或重要事务召集。日程提前可见。受命在外的人按授权安排回报，不因为主君随机开会而受到不可预见处罚。

议事依次展示势力目标、可承接任务和已有任务结果。玩家可接受分配、主动请命、提出替代方案，或在具备依据时申请延期。对话明确拒绝原因和潜在后果。

### 9.4 主命结构

每个主命至少包含发令人、目标、执行区域、期限、资金／物资、合格标准、额外奖励条件、失败后果、结算方式和相关人物。

结果不是简单二元成败。及时达成、低成本完成、超额完成、部分达成、合理延期和失信，各自产生不同结果。功绩要与任务难度、资源和效果相符，避免永远刷最便宜任务最优。

### 9.5 P1十类任务模板

送信、采购、运输、征募、操练、巡察、交涉、护送、追讨、师承试炼。一个模板可以有多个真实配置，但只改姓名和数字不计作独立剧情事件。

### 9.6 晋升条件

功绩提供资格；信任、能力、职位空缺和实际需求共同决定任用。不得设为只能靠送礼打通的隐藏门槛。玩家应能知道还缺哪一类条件，例如“已有战功，但尚未独立完成领队任务”。

晋升后引入新的决策维度，并允许委任重复事务。玩家不应从每月做三项工作，变成每月被迫点击三十项相同工作。

### 9.7 城郡治理：完整目标中的中后期

管理据点后，玩家关心可支配资金、粮食、可征用人口、守军、治安、民心与基础建设。选择税收和支出重点，安排合适的人负责农政、修缮、训练与安民；下属用真实时间与组织资源执行任务。

治理采用“确定目标—授权资源—指派人员—定期回报”的方式，复用主命系统。玩家可以亲自处理重点事务，但不必每月亲自点击所有城市的每一个设施。委任不会凭空获得资金、粮食或兵员，也不剥夺调整方针和更换负责人的权力。

征募挤占生产和恢复能力，过度征税影响民心与长期收益，驻军和工程消耗组织资源。占领城市需要稳定与整合，不能即刻无损贡献全部税粮。事件和道路把地方问题与商旅、医者、匠师等职业联系起来。

城郡治理不计入P1玩家可操作权限；P1世界AI只运行区域版需要的基本资源与守备规则，不宣称完整治理已经制作。

### 9.8 外交、势力存亡与个人归属

完整目标提供停战、同盟、援军、物资合作和归附等外交。谈判由具备权限的人发起、派实际人物执行，花费行程与时间；条款与履约能力决定结果，个人友谊可以帮助接触但不能自动替代势力利益。

下属玩家能承担使者任务或提出建议，不能绕过主君私自替整个势力缔约。玩家为君主时可确定目标、授权谈判底线和决定是否接受结果。

势力灭亡后逐一处理人物的死亡、被俘、归附、流亡和在野状态，解除不再有效的职位与主命，同时保留私人关系与本领。商铺、个人行李和军用资产按归属处理，不将一个势力的所有个人资产机械清零。

## 10. 经济、交易与资金归属

### 10.1 最小而有用的市场模型

城市商品具有库存、基础价值、需求、补充速度和当地事件修正。买入减少库存、卖出增加库存；供需变化反映在后续报价中。大额订单按分段或边际价格结算，不能先取得一份低价报价，再用它买光整个城市。

同一地点同一时刻的买卖存在价差或交易成本，立即买入再原样卖出不能凭空获利。跨城价差、关系优惠、运输效率和价格消息才是正当获利来源。

初期商品采用游戏单位“钱”“粮”“货物单位”，不声称与历史铜钱、石、斛精确换算。

### 10.2 交易决策

玩家要考虑本金、库存、载重、路费、期限、风险和市场消息时间。购买意向界面同时显示预计货价、运输开支和容量，不在确认后突然增加未展示的强制费用。

战争影响粮价和路线；城市持续需求使商旅不只依赖战争赚钱。商人可以选择较低利润的稳定订单，也可以承担高风险路线。

### 10.3 主命资金与包干收益

保留通过能力节约经费的乐趣，不把采购做成没有利益选择的行政报销模拟。

| 结算方式 | 玩家得到什么 | 资金规则 |
|---|---|---|
| 包干委托 | 完成目标后的规定奖励及允许留用的结余 | 接令时说明预算、目标、超支和结余处理 |
| 实报委托 | 固定报酬与完成奖励 | 未花资金归组织，不自动变成个人收入 |
| 自营买卖 | 利润及全部经营风险 | 使用个人或自己商铺的资产 |

任务物资有归属与预留数量。玩家可以履行、申请改约、放弃或违约，但不能利用切换界面把同一批物资同时交两次。确实允许出售任务物资的剧情，必须有明确的违约后果，不需要扩张成一套复杂审计系统。

### 10.4 商旅晋升

短工／行商 → 稳定客户 → 独立经营 → 首间商铺 → 跨区域合作。商铺带来库存、订单、雇员和资金占用，不直接等于一个不断自动产钱的建筑。

雇员可执行已有规则的路线，消耗时间并承担风险；玩家仍能处理关键经营决定。P1完成首间商铺的基本经营，不包含全国无限自动商队。

### 10.5 经济失败与恢复

经营失败会损失钱财、货物、时间和信用，但默认不因破产立即结束游戏。低门槛工作、缩小经营规模、出售个人非必要资产等方式形成恢复路径。

任务报价锁定有明确有效期；过期或库存变化时应重新确认。不得悄悄使用过时价格扣款。

## 11. 人际关系、声望与社会行为

### 11.1 两个关系维度与若干身份事实

亲近表示愿意交往的程度；信任表示愿意托付事务、传授或举荐的程度。初始范围分别为0—100。师徒、旧交、同僚、恩义、敌对、婚姻等是关系事实，不需要为每个概念增加一条可刷数值。

政治立场、职责、性格和当前处境参与请求判断。因此，朋友可以因为职责拒绝开城门；一个并不亲近的人，也可能因为信誉而签订商约。

### 11.2 建立关系

访问、共同工作、兑现承诺、分享消息、赠送合意物品、救助、切磋和学习都可以起作用。重复送同样礼物收益递减；礼物不是购买所有忠诚的万能钥匙。

重要变化提供具体反馈，例如“愿意替你引见，但尚不愿担保你的借款”，而不只有隐藏数值增减。

### 11.3 传授与举荐

请求评估资格、关系、目标人物可用时间和具体利益。拒绝后给出可操作的信息类别，如技能不足、师承关系未成立或当前出征，不必公开所有内部权重。

### 11.4 跨势力关系

相识人物加入其他势力后，私人关系不会凭空清零。可以通信、会面或调停，但敌对状态影响行动风险与请求边界。叛离的后果由实际承诺和行为产生，不是所有转职都自动被全世界追杀。

### 11.5 婚姻、结义和继承

结义与婚姻属于完整目标中的关系事件，条件为人物身份、意愿和相应关系，不作为纯属性装备。P1不承诺完整婚姻与家族系统。

本产品第一轮完整目标不包含跨世代家族经营；主角死亡结束此人的人生，可展示回顾与解锁。是否制作后代继承属于独立后续需求，不能在本轮悄悄扩大范围。

## 12. 技能成长、卡片与跨局解锁

原作将卡片收集作为独立系统，并与人物和本领联系起来。[S3] 本项目保留“经历变成可以使用或展示的成果”，而不改造成随机抽牌战斗。

### 12.1 三类成长来源

实践提高相关技能的经验；修业提供定向成长；师承和特定经历授予特殊本领。任务、旅行和交往均应支持成长，不要求所有角色反复去同一个地点刷训练。

### 12.2 六类卡片

| 类别 | 用途 | 跨局处理 |
|---|---|---|
| 人物卡 | 解锁相应人物开局 | 保留解锁记录，不继承上局资产 |
| 技艺卡 | 记录专项能力或提供生活行动效果 | 图鉴保留，实际能力由本局条件决定 |
| 秘技卡 | 个人战可主动使用的本领 | 本局重新学习或由开局经历赋予 |
| 战法卡 | 部队战的战术指令 | 同上 |
| 称号卡 | 记录成就，可能影响评价或请求 | 图鉴与本局实际身份分开 |
| 见闻卡 | 地点、人物经历和特殊事件记录 | 可在全局图鉴查看 |

卡片不是“卡组抽到才能行动”。已学本领在符合条件时可以从列表使用；气势、指挥资源、射程和状态决定能否发动。

### 12.3 P1的48张卡片预算

人物12、技艺8、秘技10、战法8、称号6、见闻4，共48张。技艺卡是专长里程碑，不代表每项技能每一级都必须对应一张卡。

每张卡必须有唯一ID、名称、类型、实际效果、取得条件、提示、图标与重复获得处理。没有实际作用或记录价值的占位卡不计入数量。

### 12.4 避免强迫多周目刷数值

跨局保留图鉴和人物选择资格；不默认把所有满级技能、资金和战法带入新人生。第一次游玩提供多种处境，不要求先刷几十小时才能体验商人或文官。

同一成就有多个触发机会时只能解锁一次；读档不重复发放当前世界奖励。单机允许玩家选择自由解锁模式，但清楚区分与常规记录，不需要服务器验证。

## 13. 修业与任务小游戏

小游戏必须服务本领和判断，不能把整个游戏变成重复手速考试。初始单局目标为约30—90秒的玩家游玩时长；这不是开发工期。

### 13.1 P1三种小游戏

| 小游戏 | 玩家操作 | 结果影响 |
|---|---|---|
| 议价筹算 | 根据货物信息和已知报价，在有限轮次内选择数量、让步或交换条件 | 限定幅度内调整价格和学习经验 |
| 军阵操练 | 观察地形与编组要求，安排队列和行动次序 | 调整训练效果、士气或主命评价 |
| 礼议应答 | 依据对象立场、话题与先前信息选择论据和回应 | 调整说服／交往结果与相关经验 |

这些是本项目原创交互，不直接复刻原作小游戏画面或题库。

### 13.2 便捷结算

通关引导后可选择自动结算，按人物技能、难度和条件给出稳定的正常结果。手动优秀表现提供有限额外收益，初始上限建议约20%，避免自动结算成为明显惩罚。

特殊卡片不能仅因玩家不擅长实时输入而永久失去；关键技能挑战可提供不依赖反应速度的等价考核。主角数值和学习经历仍然要起作用。

### 13.3 后续扩展

锻造、医案、航路和学问挑战在对应职业真正接入时制作。P1不为追求“八职业名称齐全”而做八个彼此隔离、毫无经营后果的小游戏。

## 14. 个人战

原作的个人战包含移动、朝向、武器攻击范围、气合与秘技，也存在护卫对象的胜负条件。[S4] 本项目保留这些判断维度，不以双方自动对砍的动画代替可操作战斗。

### 14.1 战场与参战规模

初始使用9×9逻辑格的2D战场，可用美术弱化格线。P1支持单挑，以及玩家与最多2名同行者对最多5名对手的护送／遭遇战。尺寸和人数是试玩前基线。

### 14.2 一轮流程

玩家选择本轮行动：移动攻击、原地防御、秘技或尝试撤离。移动攻击需要选择落点和朝向；预计可攻击区域清楚显示。

AI依据当轮可见的起始局面预先提交意图，不读取尚未执行的玩家指令来作弊。确认后按固定阶段结算：防御声明 → 分步移动与阻挡 → 普攻／秘技 → 持续状态与胜负检查。

相同速度或同时争夺位置采用可复现的平局规则；两人不能最终占据同一格。战斗详细设计需固定速度优先和路径冲突算法，并编写测试，不在UI层临时决定。

### 14.3 武器区别

刀剑侧重近身、反制与灵活；长兵依赖距离与正面控制；弓依赖射程、射界和近身压力。长兵与弓不能只成为更高攻击力的刀剑。

秘技使用气势；气势通过行动、防御和战斗过程取得。强力招式有代价和条件，不以随机抽到某张卡决定有没有可用操作。

### 14.4 胜负与失败后果

切磋重在胜负与学习，默认不会随机杀死人。护送需要保护目标或到达出口；遭遇可以脱离；特定剧情可以有更高风险，但必须提前告知。

失败可造成受伤、延误、任务失败、被俘或财物损失。主角死亡不是每次普通失败的默认结果。即使主要属性较低，位置、装备、同行者和撤离方案也应提供合理空间。

### 14.5 操作与信息

选中落点只预览，不立即执行；有独立确认。手机不依赖悬停和右键；状态原因、武器范围和撤退条件可通过点按查看。敌人精确秘技可保留未知，但已发生的伤害和状态应有可阅读记录。

## 15. 野战、攻城与玩家权限

原作合战中，军团长能操作全军，部队长仅操作自己的部队；野战和攻城也各有指令和胜负方式。[S5] 这项权限差异是人物晋升的核心体验，不能为了方便直接让所有开局都变成全军指挥官。

### 15.1 野战

P1建议使用最大18×12逻辑格、每方最多5部的小规模战场。每部有兵力、士气、训练、兵种、将领、指挥资源和状态；地图提供地形、道路、遮蔽与撤离位置。

一轮内各部依次获得行动机会。行动包含移动、攻击、防御、战法、等待和撤退。攻击射程、移动消耗、地形影响与预计效果需在确认前可见。

### 15.2 三种初始兵种

步兵适合守线和复杂地形；弓弩兵提供远程压制但需要保护；骑兵适合机动和侧击，但受地形、补给与相关物资限制。不采用永远循环相克、无视地形与将领的简单猜拳。

特殊兵种、舟师和器械属于后续扩展。P1不提供看得见却无法获得的装饰兵种。

### 15.3 指挥范围

玩家为部将时只操作本部，其他部队由其将领执行已知目标。玩家可以提议、请求支援或申请撤退，但不保证被采纳。成为统帅后可操作所辖各部，也可委任部分部队。

AI不读玩家未来操作。对己方AI的不合理行为，要提供改进战术或清楚说明职责的途径，不能靠偷偷接管全部单位掩盖问题。

### 15.4 战法

P1战法围绕鼓舞、固守、压制、佯退、侧击和局部控制展开；每项有资源、兵种、地形或状态条件。秘技与战法是不同系统的数据类型，不允许个人战招式未经定义直接作用于万人军队。

### 15.5 胜负

除击退敌军，还应有护送粮队、守住位置、突破包围与掩护撤离。士气归零导致溃退；兵力损失区分伤亡和战后恢复口径，不能把战斗结束后的兵力凭空恢复。

### 15.6 攻城：完整目标，P2接入

攻城采用“城外接近区—攻门／侧道—内城”的节点结构，共用部队、战法、士气和物资规则。玩家决定主攻方向、压制、破坏、防守轮换、围困或谈判。

胜利可能来自突破、防守方投降、解围成功或攻击方断粮撤退。不得只显示一条城墙血条让双方重复攻击。

首个攻城内容只需要一种完整可玩的城防结构；之后通过地形和节点组合变化，不急于增加专用引擎或全新3D场景。

### 15.7 战争与世界时间

每完成一轮战术行动，推进一次世界半日结算。出征人物和部队标记为战斗占用，不会在同一时刻被世界AI派去另外一座城市。

援军、运粮和道路变化在轮次边界进入战场，不在动画中途修改已执行结果。粮草只能由一个明确结算点消耗，避免战斗系统和世界系统重复扣除。

### 15.8 远方战争

玩家未参与的战斗可使用简化结算，但遵守同样的资源、兵种和胜负约束。简化结果与实际战斗不要求逐步相同，必须通过固定场景统计检查其方向一致，避免“亲自指挥必败、自动结算必胜”的系统性偏差。

## 16. NPC与势力如何生活

### 16.1 分层而不是逐帧全世界思考

人物在任务完成、地点变化、关系事件和固定决策节点重新选择行动；势力在议事、资源变化、战争和周期节点更新计划。不是每一帧对所有人物重新计算所有关系。

P1的80名人物均有合法所在地、角色职责与基本行动，但重点剧情只覆盖20名。未制作专属剧情不等于人物没有任何生活状态。

### 16.2 人物决策

从职责、个人目标、资源、位置、性格和已知消息中选择行动。只维护实际发生关系的人物边，不建立没有使用价值的全员两两好感矩阵。

可调试记录应回答“为何去此处”“为何拒绝请求”“当前在做什么”；不把内部计算日志直接显示给玩家。

### 16.3 势力决策

先检查基本守备、粮草与资金，再决定内政、人才、外交和军事目标。正常难度下，AI与玩家遵守同样的物资和行动边界；更高难度的资源修正如被采用，必须公开说明。

邻近势力可能合作也可能敌对，不能让每一个势力都只围着玩家做决定。战争行动有行军、补给与人员占用成本，避免无限出兵和瞬移。

### 16.4 防止世界很快塌缩

扩张受到占领治理、兵力恢复、补给和其他势力反应制约。首先通过正常规则控制滚雪球，不依靠到期凭空复活被灭势力。

验收时跑多种种子、不同开局和一段无人干预的世界模拟，检查是否常出现短时间同一势力碾压所有区域。如果出现，应调整决策与资源约束，而不是默认认为动态世界就是随机乱战。

## 17. 事件、历史倾向与玩家改变世界

### 17.1 两种同源模式

历史倾向模式：以核验过的开局状态与历史相关事件提高熟悉进程出现的可能，但前提不满足就改写、延后或不触发。

自由沙盒模式：使用相同开局数据和基本规则，关闭强方向性的历史事件推动。两者共用同一事件系统，不维护两套核心游戏。

### 17.2 三种事件内容

人物事件突出关系与性格；世界事件连接市场、灾情、战争和政局；职业事件检验该道路的独有选择。随机任务模板不等于剧情，不能用重复模板替代全部手写事件。

### 17.3 事件必须具备的结构

唯一ID、优先级、可触发时间窗口、参与者条件、地点条件、世界条件、可见信息、选择、效果、冷却、一次性标记、取消原因与退化方案。

条件在入队和真正展示前各检查一次。玩家读完对话时的重要参与者和交易资源应锁定到当前事件安全边界，避免显示一个选择却在确认时无声变成其他结果。

### 17.4 历史条件失效

假设某段剧情要求两个人物分别任职于两个势力，但其中一人已死亡、转仕或被俘：不能按日期强行把他恢复原状。可将剧情改成其他人物承担同类事务、转为后续传闻，或明确取消。

关键角色不可替换的专属事件直接失效；一般委托可以使用满足条件的角色槽位重新分配。两类事件不能混用。

### 17.5 示例事件：受托粮商失约

触发：玩家已接采购任务，目的地粮商因道路风险无法按约供货。

选择：寻找替代商人、协助解决运输问题、承担较高成本采购，或申请延期。各选择影响时间、资金、与商人的信任和主命结果。

这段事件可以与市场和旅行真实互动；它不是弹窗随机加减钱。事件中的金额、货物和交付状态使用游戏真实数据，不复制一套剧情专属假账。

## 18. 失败、结局与可持续游玩

### 18.1 可恢复的失败

普通任务失败、切磋落败、经营亏损和合理离职不直接结束游戏。后果应有分量，但同时保留新的选择。被俘期间提供赎回、交换、释放或适用事件，不让玩家停留在只能反复点等待的死锁。

### 18.2 人生结局

事业里程碑触发阶段结局与回顾；退休和寿终形成个人终局；高风险剧情的死亡须有充分预警。正式产品可以有统一天下结局，但其他道路有自己的完成标准。

P1结局为：获得独立领队资格、开设并完成首个商铺经营目标、完成区域见闻与人物交往目标。达到后可继续已完成内容，尚未接入的职位或地区清楚标注版本边界。

### 18.3 回顾内容

展示重要人物、师承、任职变化、旅途、决定和所得卡片，而不只有总分。记录来自真实发生的事件，不由运行时模型自由编造。

### 18.4 难度与便利

难度调节主要作用于经济宽容度、AI竞争、战斗信息与失败损失。文字速度、动画速度、小游戏自动结算、字体大小等便利选项不应承担难度惩罚。

## 19. 视觉方向、界面与跨设备操作

### 19.1 美术基线

推荐“有生活感的汉末2D绘景＋人物立绘＋清晰的现代排版”。地图、衣着、建筑与器物形成时代氛围，信息层不刻意仿古到难读。

不采用满屏金色边框、统一发光卡牌、廉价卷轴背景或SaaS仪表盘布局。人物的年龄、身份、表情与装备需要可辨识；同一人物在头像、对话和战斗中保持一致。

本轮交付文字设计，不包含已完成的游戏美术或正式UI图。

### 19.2 主界面信息层级

大地图中央保留足够空间；日期、当前身份、钱财与身体状态构成精简状态区；当前任务与期限放在可展开侧栏；人物、物品、卡片和记录放在统一入口。

城市场景保留主体建筑与活动；人物对话将“这个人是谁、当前态度、能谈什么”组织在一起。避免同一屏出现两个用途相同的搜索框或重复的任务入口。

### 19.4 桌面、平板和手机

同一套规则和内容，共用场景组件；输入与布局可以分平台调整。右键、悬停和键盘组合操作必须有点按替代。地图与战场均使用先选中预览、再确认的方式减少误触。

首轮布局以1280×720逻辑空间作为桌面基线；实际文字与触控目标应按设备尺度调整，不机械缩放全部UI。手柄导航属于完整输入目标，但不承诺P1已完成全流程手柄测试。主机平台发行不在当前范围。

### 19.5 可读性

允许调整字体和对话速度；角色姓名、商品、期限与结果不能只靠颜色区分。战场危险、归属和状态同时提供图形或文字说明。较大字体下要重新排版，不只是放大后裁切。

## 20. 内容制作规范与P1内容预算

### 20.1 不用数量掩盖内容不足

80名人物不等于80套相同模板头像；24个任务配置不等于24个独立剧情；18个事件单元要求有明确触发与结果。每项内容必须能在实际游戏路径中找到入口。

### 20.2 重点人物内容

20名重点人物各有角色定位、当前目标、关系、对话语气、至少一项有意义的互动和与系统相连的事件。其余人物提供稳定的任职、服务、任务、关系和世界行动，不伪装拥有尚未编写的专属剧情。

### 20.3 任务与事件预算

24个任务配置覆盖第9章的10类模板，并至少包含不同期限、资金结算或风险决策。18个原创事件单元由人物、职业和世界事件构成，其中至少有三条可追踪的短事件链。

历史相关内容另附出处与改编说明。未核验的历史断言不作为正式资料提交；原创支线可以使用历史人物，但要区分史实背景与虚构情节。

### 20.4 美术资源预算

P1至少具有1张区域地图、可辨识的12个据点入口、若干可组合城市背景、20名重点人物的统一风格立绘、其余人物可识别头像、三类兵种与三类个人武器的可用表现，以及48张卡片的完整视觉资源。

临时美术可以用于内部玩法验证，但对外交付不得把占位图称为正式原画。生成工具可辅助资源制作，仍需要角色一致性、时代风格、可读性与来源审核；不把实时生成图像接进每次游戏行动。

### 20.5 音频

提供主题、城市、旅途和战斗的音乐与必要交互音效。P1不做全角色语音。音频效果不能承担唯一的战斗警告，关闭声音仍应能游玩。

### 20.6 内容文件规范

人物、城市、路线、物品、卡片、任务、事件与本地化文本采用稳定ID。显示名称可修改，存档引用不能因此失效。资源清单记录作者／来源、授权信息与替换状态；开发记录可以附生成过程，游戏运行不依赖这些工具。

初期使用文本数据、表格整理和校验脚本，不先建设庞大的可视化编辑平台。

## 21. 技术选型与系统结构

### 21.1 推荐路线

Godot 4.x经过网页导出验证的稳定版本，配合GDScript与Compatibility渲染模式。具体小版本在首个工程验证后锁定，之后升级必须重新验证存档与导出，不能跟随“最新”自动升级。

Godot官方列出的游戏导出目标包括Windows、macOS、Linux、Android、iOS与Web；当前官方说明Godot 4的C#网页导出仍不可用。[S7] 因此本项目不选C#作为核心语言，也不把一个尚未验证的第三方导出分支作为基础。

网页导出当前依赖WebAssembly与WebGL 2.0，使用Compatibility渲染路径；本项目据此避免依赖其他渲染模式的特效。[S8]

网页优先单线程。Godot官方已经提供该导出路径；多线程所需的跨源隔离条件不作为P1部署前提。[S8、S11]

### 21.2 为什么不同时开发两套引擎

上一轮提出的网页优先Phaser路线仍是可行备选，但本轮设计以“完整独立游戏＋多平台”为目标，选择Godot作为推荐基线。是否改选引擎应在工程验证时基于包体、浏览器兼容和开发效率判断，不在同一项目中并行维护Godot与Phaser两个世界模拟。

### 21.3 四层边界

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 内容数据 | 人物、剧本、城市、物品、事件、文本 | 不直接操作UI与文件系统 |
| 规则与模拟 | 时间、行动、任务、关系、经济、战斗和NPC决策 | 不依赖具体场景节点播放动画 |
| 表现与交互 | 场景、立绘、声音、输入、动画和信息展示 | 不另写一套交易或战斗结算 |
| 平台适配 | 存储、文件选择、导出、窗口、浏览器桥接 | 不改变同一动作的游戏规则 |

规则层可以使用不依赖场景树的GDScript对象便于测试，但不称其为完全不依赖Godot的通用库。没有必要为了形式独立额外引入Python、Rust或另一套运行时。

### 21.4 核心模块职责

世界时钟统一推进时间；行动服务验证并提交玩家／NPC行动；人物与关系模块维护身份和关系；任务与事件模块处理目标、条件与效果；经济模块处理报价、库存和资金；战斗模块处理个人与部队战；存档模块序列化与迁移状态。

模块之间通过明确请求和结果协作。一个动作的权威结果只计算一次；动画根据结果播放，不在动画结束时再次随机计算奖励。

不使用微服务、消息队列、ECS框架或数据库服务器作为默认必需组件。新增抽象必须对应实际复杂度，而不是为了“未来可能有联机”。

### 21.5 数据实体

| 实体 | 最少需要记录的内容 |
|---|---|
| 人物 | ID、属性、技艺、身份、所在地、所属、状态、个人资产 |
| 关系 | 两个角色ID、方向、亲近、信任、事实标签、最近事件 |
| 据点 | ID、类型、设施、归属、市场、守备、已知消息 |
| 路线 | 起终点、时耗、条件、风险、运输方式 |
| 组织 | 负责人、成员、职责、资源、外交与当前计划 |
| 主命 | 发令方、受命人、目标、资金规则、期限、状态与结算标记 |
| 事件 | 条件、参与者、阶段、选择、效果、冷却与一次性状态 |
| 卡片 | 类型、条件、效果、取得记录与显示资源 |
| 战斗 | 参战者、资源、地图、轮次、阶段、队列与随机状态 |
| 长行动 | 路线／目标、剩余步骤、已消耗资源、暂停原因与预留资源 |

### 21.6 一致性与随机数

世界、事件和战斗各自使用可保存的随机流，避免打开某个界面抽取一次随机数就改变未来大战结果。金额、时间、数量与主要判定优先采用明确的整数口径。

同版本、同存档、同动作序列在网页和桌面端应产生相同规则结果；这是验收目标，需要测试证明，不是“用了同一引擎”就自然成立。

## 22. 存档、浏览器持久化与跨平台互通

### 22.1 两类保存数据

局内存档保存当前世界、人物、任务、资产、战斗、事件和随机状态；全局档案保存设置、图鉴与人物解锁。两者分开，避免删除一个周目把所有图鉴清空。

建议P1提供3个轮换自动槽、10个手动槽，并提供全局档案导出。用户可额外导出任意备份文件，不受内置槽位数限制。

### 22.2 自动存档边界

有意义的行动完成、半日结算完成、重要事件选择完成和进入重大冲突前保存。战斗在稳定轮次边界保存，不序列化播放到一半的粒子或动画。

长旅行保存已走路段、所用时间、真实地点和剩余计划；加载后可以从可解释状态继续。崩溃最多回退到最近一次已完成的保存边界，不能依赖关闭页面时才保存。

### 22.3 统一格式

使用包含格式版本与内容版本的可迁移结构，至少记录存档ID、游戏日期、剧本、人物、世界实体、任务、事件阶段、战斗状态、长行动、全局解锁关联和随机流状态。

64位随机状态和可能超出JavaScript安全整数范围的数据以字符串等无损方式保存；不要经浏览器桥接时被隐式转成失真数字。

### 22.4 正确写入与恢复

采用先写新快照、校验、再替换当前槽位的流程，保留前一份有效备份。桌面写文件与网页持久化是不同适配实现，不能只验证内存中读回成功就宣称已经落盘。

网页持久化是否成功需要专项验证与可观察结果；不能只把引擎写入调用返回当作刷新后一定存在。读档损坏时不覆盖原文件；可恢复前一份快照或导出故障文件。

### 22.5 浏览器风险

浏览器存储可能因用户清理、容量管理或隐私模式受到限制，因此本地自动保存不能作为唯一可靠备份。[S10] 本项目要求可导出文件、显示最近保存状态，并在检测到持久化风险时明确提醒。

“支持统一存档”指同版本和相容内容的结构互通，不等于自动跨设备同步。云存档不属于P1；网页与客户端使用导入导出迁移。

### 22.6 导入与版本迁移

导入先检查格式、大小、必要字段和内容版本，再生成独立槽位。不得把存档作为任意脚本或引擎资源执行。较旧可迁移版本保留原始备份；较新且不支持的版本拒绝读取，并说明需要的游戏版本，不强行猜测字段含义。

网页文件交互由平台适配层使用Godot提供的JavaScript桥接能力接入浏览器行为，核心规则无需知道文件选择器细节。[S12]

### 22.7 缓存更新

游戏资源按版本管理。发现新版本时，先允许保存，再在重新启动时切换完整资源集，不在当前游戏中混用新旧脚本和数据。缓存更新失败时保留可启动的旧版本或给出明确恢复入口。

## 23. 网页发布、平台支持与性能预算

### 23.1 网页部署

首版网页游戏通过HTTPS提供静态资源，不需要Sanic或其他游戏后端来结算每一步行动。现有Web服务器可以承担文件分发，但本设计不擅自修改或部署到用户的现有站点。

实现时配置正确的资源类型、压缩、版本缓存和错误页。启动页提供进入游戏的明确按钮，音频、全屏等行为依浏览器允许的用户交互流程触发。[S8]

### 23.2 离线规则

PWA作为网页增强目标；只有完整游戏资源已缓存并经测试，才显示“可离线使用”。资源缓存与用户存档分开管理；浏览器缓存可能被回收，不能承诺第一次访问后永久离线可用。[S8、S10]

P1仍按小而完整的区域包交付，不同时引入复杂的按需下载与无限内容包体系。扩大地图后再评估资源分包。

### 23.3 平台矩阵

| 平台 | 完整产品目标 | P1验收口径 |
|---|---|---|
| Linux桌面 | 正式支持 | 必须有实际构建和完整核心路径测试 |
| 桌面网页 | 正式支持 | Chrome／Chromium与Firefox核心路径实测 |
| Windows桌面 | 正式支持 | 尽早做构建与启动验证；未实测不宣称完成 |
| macOS桌面 | 正式支持 | 需要对应平台构建与执行验证 |
| Android原生 | 正式支持 | P1先验证触摸设计；原生完成另有验收 |
| iOS原生 | 正式支持 | 需macOS／Xcode及实际设备验证，不以模拟器代替全部验证 |
| 手机浏览器 | 网页目标的一部分 | Android和iOS浏览器分别记录结果，不由桌面结果推断 |

Godot支持目标平台，不等于本项目自动获得每个平台的质量结论；尤其iOS导出存在明确的macOS和Xcode环境要求。[S7、S9]

不把其他项目的Android最低版本、Android TV遥控器规范或Linux发行版支持范围带入本项目。最低系统与浏览器版本根据本项目实测建立。

### 23.4 初始性能预算

以下仅为工程验证的起点，必须附测试设备、浏览器、数据规模和测量方法，不能单独当作承诺。

| 项目 | 初始目标 |
|---|---|
| P1完整区域首次传输体积 | 压缩后不超过80MB，字体与音频包含在内 |
| 日常界面帧率 | 常规桌面目标60帧，受限移动设备目标30帧 |
| 单次半日模拟 | 桌面95分位不超过100ms，移动设备不超过300ms |
| 连续时间推进 | 超过短时操作预算就显示进度，允许在安全节点停止 |
| 资源使用 | 不预加载所有大尺寸立绘和全部音乐 |
| 图集 | 初期单张图集以不超过2048×2048为预算起点 |

如网页包体或性能达不到目标，先优化资源尺寸、数据查询和模拟调度，再评估导出模板；不直接删掉NPC、职业或战斗来“解决性能”。确需调整产品范围，必须回到设计评审。

### 23.5 降级与错误反馈

缺少必要浏览器能力时，启动页说明环境要求；资源下载失败可重试；持久化失败仍允许导出；窗口过小时提示或调整布局。不能用一片黑屏或持续转圈替代错误处理。

## 24. 可验证的验收标准

### 24.1 首要完整游玩路径

一个在野人物应能获得生活来源，出城旅行，交易与认识人物，学习一项本领，选择出仕或独立经营，完成实际任务与战斗，发生身份和关系变化，取得卡片与阶段成果，存档后继续。

这条路径必须从真实标题菜单开始，不依赖开发者手工修改JSON或在控制台跳关。

### 24.2 P1必须通过的场景

| 测试ID | 场景 | 通过标准 |
|---|---|---|
| A01 | 在野谋生至仕途阶段结局 | 合法获得资源、任职、立功与领队资格 |
| A02 | 行商至商铺阶段结局 | 报价、载重、运输、结算和经营目标完整 |
| A03 | 从仕途转入商旅 | 技能与个人关系保留，公职权限正确移除 |
| A04 | 包干采购的不同解法 | 本地采购与跨城采购均可完成且收益／时间不同 |
| A05 | 已收预算后放弃任务 | 资金、货物与后果按明确规则处理 |
| A06 | 个人战的距离与朝向 | 相同属性下，不同选择能改变合理结果 |
| A07 | 护送战保护目标 | 胜负基于护送条件，不只检查玩家生存 |
| A08 | 部将和统帅权限 | 部将不能越权操作友军，统帅可按权限指挥 |
| A09 | 世界时间推进 | NPC行动、库存、期限与战斗时间不重复结算 |
| A10 | 事件前提失效 | 人物死亡／转仕／地点失效后不会强制原剧情 |
| A11 | 网页刷新与异常退出 | 回到最近有效快照，不复制奖励或丢失此前存档 |
| A12 | 网页→Linux→网页 | 同内容版本存档往返后关键状态一致 |
| A13 | 随机状态恢复 | 保存、加载后相同动作产生相同规则结果 |
| A14 | 存档损坏／版本不支持 | 原始文件保留，明确提示并提供可用恢复路径 |
| A15 | 小游戏自动结算 | 不出现职业主线永久不可完成或明显被迫手动刷取 |
| A16 | 触摸核心路径 | 不依赖悬停、右键或键盘完成核心操作 |
| A17 | 市场防重复结算 | 连点、过期报价和重载不复制货物或资金 |
| A18 | 零钱财、受伤或失业 | 有符合设计的恢复路径，不进入无解状态 |
| A19 | 新旧网页资源更新 | 不混载不同内容版本，切换前可保存 |
| A20 | 长时间世界模拟 | 不出现负库存、重复任职、无故复活或同人多地 |

### 24.3 玩法质量检查

至少比较两种主命完成路径、两种个人战位置选择和两条职业成长路线。每个系统应提供实际决策，而不是更高数值永远唯一最优。

还应试玩低武力文官、高武力低商术人物和资源较少的商旅开局，检查角色差异是否真实存在，以及各自是否有可行道路。

### 24.4 报告格式

每个平台报告区分：已导出、能启动、核心路径通过、长时间测试、尚未覆盖。记录构建版本、操作系统、浏览器或设备、存档版本和复现步骤。

本轮没有游戏构建，以上测试均为未来验收要求，未声称已通过。

## 25. 制作顺序与交付件

### 25.1 接下来的设计交付

总体方案评审后，将其拆为可独立检查的系统详细设计：世界时间与行动、人物与关系、任务与经济、个人战、部队战、事件与存档、UI状态与平台适配。

详细设计应包含数据结构、状态转换、具体结算顺序、参数表、异常路径和测试用例。不能拿UI图代替这些内容，也不需要在玩法尚未确认时先编出大量函数名。

### 25.2 工程验证

先验证一个真实人物能完成城内行动、一次旅行、一次交易、一次时间推进和保存；同一小工程导出Linux与网页并读回同一份存档。验证输入、包体与保存后，再锁定Godot小版本。

该工程验证不应宣称P1完成，也不应先堆入80名人物来掩盖规则缺陷。

### 25.3 完整切片

接入一条主命链、一次师承、一个关系分支、个人战和部队战，再打通仕途与商旅的阶段结局。形成可从标题菜单完成的真实游戏流程。

### 25.4 内容扩充与正式资源

在数据契约稳定后补充人物、任务、卡片、地图和正式资源；功能、美术、剧本与测试可以按接口并行。每批新增内容都经过数据校验和可达性检查。

### 25.5 每次交付必须包含

源代码、内容数据、资源来源说明、导出设置、使用说明、对应版本测试记录，以及实际生成的构建。文档和不可再生成的资源纳入版本控制；平台SDK、缓存和可再构建产物不必全部塞进源码仓库。

远端仓库地址、托管域名和发布账号不是本文擅自作出的决定；用户未指定和授权前不写入其现有项目。

## 26. 主要风险与控制方式

| 风险 | 早期信号 | 应对方式 |
|---|---|---|
| 变成普通三国SLG | 所有开局都在管城征兵 | 用人物权限、城市生活与非仕途结局验收 |
| 首版过小而失去参照玩法 | 没有修业、卡片或可操作个人战 | 缩地图和内容数，不删除P1承诺的玩法 |
| 过早追求八职业齐全 | 每条路线只有一两个独立按钮 | 两条路线先完整，其他保留明确后续目标 |
| 历史与沙盒矛盾 | 人物无故复活、突然换势力 | 条件化事件、快照审校与失效分支 |
| 市场和任务漏洞 | 同城倒买倒卖、重复交货 | 边际报价、资源归属、一次结算与回归测试 |
| NPC失控或无趣 | 人人挂机或区域迅速一统 | 有目标的有限模拟、资源与扩张约束 |
| 网页性能差 | 包体大、长时间白屏、每次结算卡死 | 网页从第一轮验证，压缩资源与分段结算 |
| 存档失去可信度 | 刷新丢档、版本更新不兼容 | 稳定边界、有效备份、迁移与往返测试 |
| 美术不一致 | 同角色多种长相、设施无法辨认 | 角色规范、样板确认与资源审核 |
| 范围膨胀 | 先做账号、联网、平台化编辑器 | 以单机核心路径与版本边界拒绝无关扩张 |

## 27. 一段用于检验设计的完整游玩例子

以下是虚构演示情节，用来检查系统之间是否真正相连，不作为史实叙述或已实现游戏录像。

玩家使用自建人物开局，武力普通、交涉较好，身上只有少量钱。在城内做半日短工后，获得继续旅行的资金，并通过酒肆消息知道某处有采购差事。

他可以直接找到办事人员接受低门槛委托，也可以先拜访一名熟人争取举荐。后一种选择会多消耗时间，但后续任务条件可能更好。

收到一份包干购粮委托后，玩家发现本地价格偏高。通过查看带有日期的外城行情，他决定出城采购；确认界面说明路费、预计耗时、载重和剩余期限。

途中出现一段道路风险消息。玩家选择绕行，不进入战斗，代价是多花半日与路费；另一名偏重武力的玩家可以选择雇用较少护卫直行，承担个人战风险。

到达目的地后，玩家与粮商谈价，使用手动小游戏取得小幅优惠，也可以用自动结算获得正常结果。交易按实际库存和购买数量计算；剩余运力不足时不能直接买下全部粮食。

当地一位擅长交涉的人物愿意传授本领，但需要建立基本信任。玩家可以利用剩余日程完成一次小委托后学习，也可以为了按期交粮放弃这次机会。

回到出发城，系统根据数量、期限、预算和已约定的包干条款结算。玩家获得功绩、人际信任、允许留用的结余及相应经历记录。

之后他可以接受举荐进入势力，逐步获得带队机会；也可以把钱投入下一次交易。入仕路线最终使他在野战中指挥自己的一个部队，而不是无条件接管全军。商旅路线则使他建立稳定供货关系，完成首间商铺的经营目标。

保存后把存档文件导入另一平台，人物、任务、库存、关系、时间与已走过的路保持一致。上述过程应由真实规则发生，不靠一串固定剧情强行演示。

## 28. 当前结论与评审重点

推荐保留：个人身份为中心、自由旅行与设施生活、多职业、议事主命、技艺与卡片、修业小游戏、个人战、野战攻城、动态人物与条件化事件。

推荐采用：单机2D、Godot＋GDScript、网页从首个工程验证开始参与、统一存档、无强制账号与后端、基于完整游玩路径验收。

推荐P1范围：12个据点、80名人物、在野与两条主要成长道路、48张卡片、3类小游戏、个人战与小规模野战、真实阶段结局和网页／Linux存档互通。

最需要评审的不是暂定工作名或某个基础数值，而是两点：本方案是否保住了用户所说的《太阁立志传5》玩法结构，以及P1在可控内容规模内是否已经形成一个真实、可继续游玩的人生。

**当前完成状态：总体设计文档已形成；游戏代码、正式UI图、实际构建、部署和平台测试尚未开始。**
