# 汉末行记｜视觉参考与内容驱动工程方向 v0.3

**日期：2026-09-09。性质：工程方向补充与架构建议，不是已经实现的框架、编辑器或新试玩版。**

上位玩法基线继续采用v0.2的“场所—人物—交谈/观察—行动—世界反馈”。本文不重写既有经济、时间、职业和战斗数值，也不覆盖已有总体方案与详细设计。用户提出的两项方向是：实际研究截图与实机过程；建立统一游戏底层和内容编辑流程，不再连续制作互不相同的演示。

## 1. 本轮参考研究的真实范围

视觉理解需要真实像素；搜索标题、视频简介、字幕或官方文字不能替代观看。静态截图可以支持画面组成的观察，不能独自证明转场顺序、点击次数、NPC自主行为、动画节奏和事件触发概率。

### 初步视觉观察与设计含义

1. 原作使用菜单和设施卡片，并非完全无菜单。关键是画面仍然呈现具体地方和正在打交道的人。保留我们的情境菜单，不把目标误改为“消灭所有列表和按钮”。
2. 酒肆官方截图中，内景占主要空间；人物、对白与有限指令直接叠加其上。这支持“场景优先、人物成为当前焦点”的构图方向，而非固定侧栏加工作面板。
3. 商家、街道与不同室内背景提供场所辨识。由此建议我们给场所模板规定空间、人物位、物件热点和界面遮挡边界，而非只切换一张网站背景。
4. 静态截图里的路人不证明复杂昼夜生活模拟。我们的NPC在场、换班、关系反馈属于已认可的本项目设计，不能一律宣称是原作逐项复刻。
5. 原版和DX、PC与主机显示方式应分开标注；修改版和玩家事件脚本不能自动视为原版机制。历史建筑、服饰和器物仍需三国化，不能照搬日本室内。

### 下一轮实机拆解的固定记录格式

每个条目记录：版本/平台、来源、实际检查的时间段或帧、进入前状态、玩家输入、场景/人物变化、规则结果、返回位置，以及“直接观察/文字佐证/推测/本项目改进”。无连续画面时不填写虚构时间戳。

优先覆盖：城镇进入与退出、设施内换对象、普通交易与议价、工作受领和回报、正式议事、人物不在与拒绝、拜访和学习、城中/途中遭遇、个人战的进入与返回、熟访快捷操作。重点采样第一次与重复办理的区别，不只收漂亮截图，也不把宣传剪辑当完整流程。

## 2. 工程目标：同一个游戏，逐步增加内容

固定交付对象为一个Godot/GDScript正式项目。桌面与网页来自同一规则核心和同一内容集。独立HTML预览作为历史体验实验归档，不再沿它扩写第二套正式经济、任务和存档规则。

底层先行不是先制作一个通用游戏引擎。Godot承担绘制、场景、音频与基础输入；我们建设本游戏专用的世界、场所、人物、交互、任务和内容工具。

“只做一座城”应改写成：先使通用框架能加载一座用编辑器制作的城，再用同一编辑流程加入另一处场所和不同任务，以证明可扩展性。城是框架的验收内容，不是另写一个短命演示。

已有源码与测试先审查后决定迁移。本文未执行新一轮源码审计，不声明旧程序已经满足以下全部接口。

## 3. 先分清三种数据

**内容定义**描述“设计上有什么”：人物身份、初始属性、城镇与通路、岗位、商户、对话图、任务目标、事件条件、资源引用。

**运行状态**描述“这局实际怎样”：当前日期、人物位置与伤病、在场岗位、关系变化、库存、承诺、任务进度、已知消息、对话继续点和随机状态。

**表现数据**描述“怎样呈现”：内景、人物站位、立绘表情、热点、音效和短演出。显示结果不再次改变钱货或任务。

定义与状态通过稳定ID关联。改显示名、换立绘或改场景布局不能改变人物身份；商户库存不能因为换了当值伙计复制一份。编辑内容定义不是远程修改所有玩家已经开始的周目。

## 4. 第一批基础模块

| 模块 | 必须先形成的能力 | 当前不要求一次做完的内容 |
|---|---|---|
| 内容目录与装载 | 稳定ID、引用、版本、字段校验、资源映射、内容包装载 | 在线模组商城和账户系统 |
| 世界时间与行动 | 半日推进、行动占用、中断/恢复、统一提交、稳定保存边界 | 每位人物逐秒完整生活仿真 |
| 地图与旅行 | 路网、位置、可达性、费用、行程和旅行中断 | 全国全部地域和复杂天气仿真 |
| 城镇与场所 | 层级、通路、准入、内景、热点、物件、在场人物 | 每座城市全部独特美术和大量空房间 |
| 人物与关系 | 定义/状态、属性、身份、岗位、关系、可用性与基本活动 | 80人全部专属剧情 |
| 交互与对话 | 对象上下文、说话人、条件话题、分支、调用行动、结果返回、继续点 | 无限制通用编程语言、运行时大模型 |
| 任务与事件 | 来源、发现、受领、目标、回报、期限、失败/取消、条件触发 | 全部职业任务和历史事件正文 |
| 经济与物品 | 物品、钱包、容器、所有权、库存、报价和一次成交 | 全国封闭宏观经济 |
| 存档与平台适配 | 版本快照、真实持久化、恢复、Linux/Web共同逻辑与实际往返 | 未实测的全平台完成声明 |

模块是职责边界，不要求每一项都做成一个庞大的框架包。更不能只建同名文件夹和空接口就宣布基础完成。

### 共同状态查询与行动执行

对话、任务、事件和编辑器调试使用同一组已定义条件：人物是否在场、技能是否达标、岗位是否有权限、任务是否已接受、物品是否可用等。不能四处复制不同判断。

对话节点可以申请“开始受领”“打开当前商户的货单”“交付任务”“推进课程”等命令，但动作由对应规则模块验证、经世界核心提交。选择一句台词不直接向玩家钱包加预算；任务经费只能按受领流程授权。

同一提交保存结果及去重身份；跳过对白、关闭交易面板或恢复存档只恢复已发生事实。失败原因返回上下文中的适当话语，不静默转成成功。

## 5. 编辑器作为基础交付

推荐在Godot编辑器中增加本项目内容工具，不另做一个网站后台，也不重新制作绘图/场景引擎。官方EditorPlugin、Inspector扩展和GraphEdit提供可利用的控件及接入方式，但它们不会自动成为完整对话或任务编辑器；业务语义和保存校验仍需实现。[S5—S7]

| 编辑区域 | 内容制作者能够完成什么 |
|---|---|
| 世界地图 | 放据点、连接道路、设置时耗和通过条件，检查路径 |
| 场所 | 设置城市入口和房间通路，放人物锚点/物件热点，编辑准入及入口事件 |
| NPC与岗位 | 新增人物、属性、身份、服务权限、初始位置、形象、关系和对话入口 |
| 对话 | 编辑说话、选择、条件、行动调用、分支和结束节点，切换当前说话人 |
| 任务与事件 | 设发令/受理/验收对象、目标、期限、预算、触发、失效和分支结果 |
| 测试与诊断 | 选测试初始状态，从指定地点运行；显示分支失败原因、动作结果、引用错误与恢复结果 |

第一版编辑器需要最基本的保存/载入、复制内容、撤销/重做、引用选择和错误定位。场所可复用Godot现有场景工具，人物可用表单，对话使用节点或结构化分支视图，任务使用目标/条件表单；不把所有东西硬塞进一种巨型蓝图。

“有JSON可手工改”不等于可视化编辑器交付完成；仅有节点画布但无法运行真实任务，也不算完成。

### 内容存储建议

沿用此前稳定ID的UTF-8 JSON作为玩法内容唯一可写源，编辑器负责读写这些文件；Godot场景和资源清单负责可视资源。可利用Resource作为编辑适配，但不另维护第二份相互竞争的NPC/任务真值。

编辑器 → 结构/引用校验 → 规范化内容数据与资源清单 → 同一个运行核心 → 原生/网页构建。

游戏包不包含编辑器面板。运行时不依赖外部编辑器服务。编辑器预览必须运行真实规则，不再以JavaScript独立模拟一份经济系统。

## 6. 内容脚本与新机制的分界

已有能力内的NPC、城镇、对白、任务分支、事件、物品和数值，通过数据与编辑器组合，不修改核心程序。

新机制仍需代码。例如从未支持过的水战规则、新型战斗目标或新的物品行为，需要增加规则实现、测试和编辑器可选项。不能许诺一套简单任务编辑器能够无代码表达任何未来玩法。

建议先提供有限的声明式节点：说话、选项、条件、调用已有动作、等待动作结果、跳转、结束。内容中的“效果”使用已登记、带参数类型的领域操作，不对字符串直接eval。新动作加入后才开放对应编辑器节点；未实现的战斗节点必须被校验拒绝，不能自动返回胜利。

剧情不等于一张固定状态图片。可以安排说话人切换、人物入场/离场、表情、消息送达、场景过渡；涉及真正位置、时间或资源变化时必须走同一规则核心。

## 7. 用第二份内容检验框架，而不是复制第一份演示

第一份验收内容：官署有人受理采购、玩家与商人交易、回到合同地点交付、再次见到经办人时得到符合经历的反馈。

第二份验收内容：由内容制作者在编辑器中新建另一名NPC、一处可进入场所和一项使用不同目标模板的送信或寻人事务。加入条件对白和一个不能当面受理的分支，不复制硬编码购粮脚本。

验收重点：添加第二份内容时，规则核心和场景控制器没有出现按新人物名、城市名或任务ID硬编码的分支；只增加内容与合法素材文件。已有核心能力不够时，明确登记为新机制开发，而非隐藏在对话事件里乱改世界。

这也检验内容是否能脱离原作者继续生产：接手的人只需要学习编辑器和内容规范，不必先理解全部经济与存档源码。

## 8. 战斗与战争如何随后接入

现在固定战斗与世界的接口：来源行动/事件、参战人物或部队ID、位置、目标、控制权限、时间和物资归属；退出时返回已结算的胜负、损失、俘虏、占用释放、任务事实和返回场所。

个人战、野战和攻城使用各自规则，不强制抽象成完全相同的行动算法。共用的是人物身份、资源、时间、任务事实、结果与保存约定，而不是所有战斗细节。

未开发战斗时，只开放不依赖战斗的验证内容；测试替身只能在测试目录使用，不能把自动判胜放入正常游戏冒称战斗可玩。新增实际战斗模块应通过这些边界加入，不推翻人物、对话和任务系统。

## 9. 后续顺序及完成门槛

| 阶段 | 产物 | 通过标准 |
|---|---|---|
| A 参考与架构收口 | 视觉/流程对照、共同数据、接口、编辑流程 | 直接观察与推测分开，v0.2NPC原则落到核心而非只换美术 |
| B 真正可运行的基础 | 内容加载、场所/人物/对话/行动/任务及保存，早期Linux/Web导出 | 一条使用正式核心的实际流程可运行；构建阻塞不再用另一套规则绕过去 |
| C 最小内容编辑器 | 地图/场所/NPC/对白/任务编辑与校验预览 | 从工具保存的内容可以被正式运行核心加载，不只是界面样稿 |
| D 可复用性与体验验收 | 两组不同内容的完整流程、恢复、异常与熟访 | 不改核心可加第二组内容；人物缺席、过期和读档都按统一规则处理 |
| E 内容与战斗扩展 | 更完整城市、人物、事件、职业、战斗模块 | 新模块沿约定接入，已有流程不被每轮重写 |

B与C按接口共同推进：每做一种内容类型，就同时具备最小编辑和运行验证；不用等全国游戏完成再补工具，也不空转制作大而全编辑平台。

资源规范确定后，场景样板和人物美术可与基础工作并行。但它们不作为规则和编辑器验收的替代。现有P1最终内容预算保持，当前调整的是生产方式及前置门槛。

## 10. 必须落地的工程检查

- 定义与实例分离；显示名变化不破坏稳定ID；人物没有第二个独立位置。
- 所有状态修改走同一规则入口；预览不改钱、不抽玩法随机、不触发奖励。
- NPC不在/越权、无来源任务、未知引用、条件字段不存在等给出可定位错误。
- 编辑器校验能发现明显断链和无出口，复杂世界状态下的可达性仍需实际测试，不能用静态检查声称全部剧情可达。
- 在对话分支、行动中断、任务受领和场所转换的稳定点保存并恢复；重开不复制事实。
- 编辑器可从独立测试快照运行，调试改值不污染正式存档。
- Linux与网页使用同一内容版本与规则；存档版本、内容兼容和迁移明确声明。
- 正式基础版本开始维护迁移规则；旧独立HTML实验档不默认宣称可被Godot加载，需单独验证迁移或明确不支持。
- 所有具名类、函数、方法有职责说明；代码、内容、计划、测试证据保持同一版本控制来源。
- 可运行版本来自正式工程导出；早期样例仍是同一产品的一部分，不再每次新建一套产品。
